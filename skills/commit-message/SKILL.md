Напиши сообщение коммита для текущих изменений. Пожелание пользователя: $ARGUMENTS

## Что смотреть

1. `git diff --cached` — что войдёт в коммит. Если в индексе пусто, смотри `git diff` и скажи пользователю, что изменения ещё не добавлены в индекс.
2. `git log -n 10 --format=%B` — как уже оформлены коммиты в репозитории: какие scope встречаются, есть ли номера задач.
3. Имя ветки (`git branch --show-current`) — в нём часто есть номер задачи (`PROJ-123`).

## Формат

```
<type>(<scope>): <тема>

<тело>

Refs: <задача>
```

- **type** — латиницей, одно из:
  - `feat` — новая возможность для пользователя;
  - `fix` — исправление ошибки;
  - `refactor` — изменение кода без изменения поведения;
  - `perf` — ускорение;
  - `test` — только тесты;
  - `docs` — только документация;
  - `build` — сборка и зависимости;
  - `ci` — конвейер CI;
  - `chore` — прочая служебная работа.
- **scope** — латиницей, строчными: модуль или область (`auth`, `api`, `ui`). Бери из истории репозитория; если изменение задевает всё сразу, scope опусти.
- **Ломающее изменение** — `!` после scope (`feat(api)!: …`) и футер `BREAKING CHANGE: <что сломается и как мигрировать>`.
- **Тема** — по-русски, до 72 знаков вместе с префиксом, со строчной буквы, без точки в конце. Глагол в прошедшем времени, совершенный вид: «добавил», «исправил», «убрал». Говорит, что изменилось, а не какие файлы тронуты.
- **Тело** — по-русски, через пустую строку, строки до 72 знаков. Объясняет, почему понадобилось изменение и что было не так раньше; как именно сделано — только если это неочевидно из диффа. Для мелкой очевидной правки тело не нужно.
- **Футер** — `Refs: PROJ-123`, если номер задачи известен из аргументов, ветки или от пользователя. Номер не выдумывай.

## Пример

```
fix(auth): отзывал refresh-токен при выходе

После выхода старый refresh-токен оставался рабочим, и сессию
можно было продлить с другого устройства.

Refs: PROJ-123
```

## Чего не делать

- Не смешивай в одном коммите несвязанные изменения: если дифф распадается на части, предложи разбить его на несколько коммитов и дай сообщение для каждого.
- Не пиши общих тем вроде «правки», «обновил код», «fix bug».
- Не перечисляй в теле изменённые файлы.

## Результат

Покажи готовое сообщение в блоке кода. Коммить сам, только если пользователь об этом попросил: `git commit -F <файл>` с сообщением во временном файле, чтобы сохранились переносы строк.
